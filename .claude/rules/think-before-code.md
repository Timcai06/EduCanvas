# 反射思考规则（写代码前必须执行）

## 写代码前的 5 问（每次修改源码前在思考中回答）

1. **我要改的是什么？** 用一句话说清楚这个函数的单一职责。
2. **谁会调用它？** 列出所有调用方，确认改动不会破坏它们。
3. **最坏情况是什么？** 输入为 null、空数组、超长字符串、并发请求、网络超时——会怎样？
4. **我是不是在造已有的轮子？** 项目里有没有类似逻辑可以复用？
5. **如果这段代码出了 bug，怎么回退？** 改动是否可逆？影响范围多大？

## 写完代码后的 3 问

1. **测试能否证明我修了 bug？** 不是「代码改了」，而是「行为变了且测试能区分」。
2. **有没有引入新的隐式假设？** 比如假设数组非空、假设时区是 UTC、假设网络正常。
3. **六个月后另一个人看这段代码，能理解为什么这样写吗？** 如果不能，加注释说明「为什么」而非「是什么」。

## 复杂决策时使用结构化思考

遇到以下情况，必须先列出至少 2 个方案再选择：
- 新增一个函数/模块的职责划分
- 错误处理策略（重试 vs 降级 vs 抛出）
- 数据结构选择（Map vs Object vs Array）
- 任何涉及并发、时序、竞态的逻辑

格式：
```
方案 A: ...
  优点: ...
  风险: ...
方案 B: ...
  优点: ...
  风险: ...
选择: A/B，因为...
```
