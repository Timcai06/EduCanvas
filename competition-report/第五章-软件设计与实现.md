## （一）总体架构设计

### 1、架构概述

系统采用 **monorepo 模块化单体**：可运行组合根位于 `apps/`，可复用协议、运行时和领域能力位于 `packages/`，共 18 个内部包 + 4 个应用。跨包依赖由包策略文件（`package-policy.json`）机器强制，公开出口与依赖例外不允许随意扩大。

```text
apps/
  web        Next.js 浏览器应用 + BFF 兼容层（学生主入口）
  gateway    gateway.v1 HTTP 组合根（多入口控制面）
  worker     持久后台任务（文档转换等）
  tui / telegram   桌面终端与渠道实验入口

packages/（核心）
  agent-runtime     唯一 Agent Loop（TurnApplicationService、Context Engine、Tool Kernel）
  model-gateway     唯一 Provider Adapter 边界
  teaching-core     教学状态机、掌握度、可信学习事件
  canvas-protocol   Canvas Artifact 契约（zod schema）与判分协议
  asset-processing  MinerU 客户端与资产解析
  gateway-core/-runtime   协议 Schema 与路由执行
  db                Drizzle schema 与 migrations（唯一事实源定义处）
  experiment-runtime  隔离执行运行时（Docker 底座）
```

一次教学 Turn 的生命周期：

```text
学生输入（文字/语音）→ 入口适配 → TurnApplicationService
→ Context Engine 组装（画像偏好 + Notebook 资料 + 掌握度投影）
→ AgentLoopEngine 调用 Model Gateway → 流式验证 → 工具调用（检索/产物生成）
→ Artifact 提案（zod 校验）→ 消息与账本落库 → SSE 投影到浏览器
→ 学生交互提交 → 服务端重校验 → 确定性判分 → 掌握度更新 → 下一步推荐
```

### 2、技术选型

| 层 | 选型 | 版本 | 选择依据 |
|---|---|---|---|
| Web 框架 | Next.js + React | 16.x / 19.x | App Router 服务端组合，BFF/SSE 兼容层保护浏览器协议稳定 |
| 语言/运行时 | TypeScript / Node | ≥24.18 | 全栈同语言，类型即契约；版本门禁脚本强制 |
| 数据库 | PostgreSQL + Drizzle ORM | — | 关系模型承载教学事实；migration 只前进不手改 |
| 校验 | zod | 4.x | 运行时契约校验贯穿 Provider 响应、Artifact、客户端提交 |
| 文档解析 | MinerU（自部署服务） | hybrid 引擎 | 中文教材 OCR/公式/表格最强，纯 CPU 可跑 |
| E2E | Playwright | — | fake-provider CI 化端到端验收 |
| 单测/集成 | Vitest | — | 593 个测试文件 |

## （二）核心模块设计

### 1、数据模型设计

数据库按领域划分为 22 个 schema 模块、72 张表（60 个 migration 管理演进），核心域：

| 域 | 代表表 | 说明 |
|---|---|---|
| 身份账号 | web_users, web_sessions, web_user_profiles | 一个自然人一个长期身份 |
| 学习者画像 | learner_profiles | age_band 五档 + grade_band 三档 + declaration_source 闭集，CHECK 约束保证合法值 |
| 对话运行 | turn, conversation_messages, agent_runtime_* | Turn 终态持久收敛；K12 可见事实与运行态显式分层 |
| 互动产物 | artifact*（immutable version + provenance） | 版本不可变，判分走 grading 协议 |
| 资产管线 | asset*, derived representations | 原件+派生表示分离，manifest 记录图片哈希 |
| 教学事实 | study*, learning* | 掌握度与学习事件只经领域事件写入 |
| 合规 | audio_consent | 音频留存监护人单独同意记录 |
| 网关治理 | gateway*, mcp_intent* | Operation 幂等、审批、恢复账本 |

### 2、Web 功能模块设计

学生端按功能域组织于 `apps/web/features/`：

| 模块 | 页面功能 |
|---|---|
| experience-mode | general/restricted 体验模式门禁（监护人确认流） |
| study | 学习偏好设置（五维画像输入） |

| canvas | 互动产物渲染注册表（quiz/classification_game/pipeline_flow…） |
| celebrate | 答题激励反馈动效 |
| assets / workspace | 资料上传与统一工作台 |
| learning / progress | 学习会话列表与进度视图 |
| voice | 听写与实时语音入口 |
| profile / settings | 画像与个人设置 |

### 3、关键实现难点与解决

| 难点 | 解决方案 |
|---|---|
| 流式输出的可靠性 | Provider 流先验证后投递；Assistant delta 写同一消息账本，断线可恢复 |
| 文档解析长耗时 | 异步三步协议 + 有界轮询 + Durable Worker，失败降级明确标记 |
| 模型生成内容的不可信 | 双端契约校验（生成时 + 提交时），判分纯函数化 |
| 多入口状态分裂 | 所有入口收敛到同一 Turn 执行语义与消息账本 |
| 未成年合规粒度 | 同意事项拆分建模（音频留存单独 consent 表） |

## （三）软件测试

### 1、测试策略总览

采用四层测试金字塔，全部进入 CI：

```text
E2E（Playwright，19 spec）        ← fake-provider 驱动的浏览器全链路
集成测试（fake MinerU/fake ASR）  ← 故障注入：超时/损坏/穿越/解包炸弹
单元测试（593 个测试文件）         ← 领域函数级，含边界测试（包策略/文件治理）
质量证据（15 份 evidence 文档）    ← 每条交付线的验收边界与"未验证项"清单
```

### 2、特色实践

- **故障注入常态化**：MinerU 管线的超时、重试、结果损坏、路径穿越、解包炸弹、secret containment 均有专门 CI 用例；真实 GPU 服务只做受控 canary；
- **跨平台边界测试**：包所有权、公共出口、文档链接有机器检查（`pnpm test:tooling` / `pnpm file:check`），架构约束不靠自觉；
- **诚实的未验证标记**：真实 Provider、Safari、真人麦克风等项在证据文档中显式标注"未验证"，不混入已完成结论——测试文化的目的是让"可信"可以被检查。
