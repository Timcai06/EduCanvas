# ADR-0010：资产解析异步化与解析器归位

- 状态：`accepted`
- 日期：2026-07-26
- 负责人：@Timcai06

## 背景

来源上传的解析目前完全在 HTTP 请求内同步执行（`apps/web/server/assets/asset-upload.ts`）：
检测类型 → 读全部字节 → 抽取文本 → 单事务写 asset + version + representation，
全部完成后才返回响应。

三个问题：

1. **上传时延与文件大小线性相关。** PDF 与 DOCX 的抽取都是 CPU 密集的同步过程，
   10MB 上限下已经能明显拖慢响应；一旦放宽上限或引入 OCR、音视频转写，请求必然超时。
2. **失败没有重试位置。** 抽取失败即写入终态 `failed` 版本，用户只能删掉重传。
3. **`asset_processing_jobs` 名不副实。** 这张表（`packages/db/src/schema.ts`）已经具备
   `status / attempts / queue_job_key / failure_code` 和完整生命周期约束，但当前只在
   `asset-repository.ts` 的 `createUploaded` 里写入一条**已经终结**的记录，是同步解析的
   事后审计，不是队列。表的形状在为异步做准备，实现却没跟上。

同时存在一个结构约束：`apps/worker` 的依赖只有 `packages/*`，全仓没有一处从 worker
导入 `apps/web`。而解析器（`unpdf` / `mammoth` / UTF-8 纯文本）当前住在 `apps/web`，
worker 够不到。

## 候选方案

**A. 解析器移入新的 `packages/asset-processing`，worker 消费队列。**
职责单一：字节进、结构化文本出，不碰数据库、不碰 HTTP。`unpdf` 与 `mammoth` 两个重依赖
只出现在这一个包里。代价是新增顶层目录。

**B. 解析器塞进现有 `packages/agent-runtime`。**
不新增目录，但 agent-runtime 是教学与 Agent 运行时，塞文档解析器职责不清；且所有引用
agent-runtime 的包都会被动继承 `unpdf` / `mammoth`。

**C. worker 通过内部 HTTP 端点回调 web 执行解析。**
无需搬动代码，但让 worker 依赖 web 的可用性与鉴权，把一个进程内的纯函数调用变成
跨进程 RPC，故障面显著变大。

**D. 维持同步，只把 `asset_processing_jobs` 写成真实任务记录。**
成本最低，但三个原始问题一个都没解决。

## 决定

采用 **A**。

- 新增 `packages/asset-processing`，只导出纯函数式解析器与其稳定失败码；
- 上传请求内只做：类型检测（魔数/受限扩展名）、落对象存储、写 `processing` 状态的
  asset + version、写 `queued` 的 `asset_processing_jobs`、入队 `assets:extract_text`，
  然后**立即返回**；
- worker 认领任务、调用解析器、把结果作为文本 representation 追加，并把 asset 推进到
  `ready` 或 `failed`；
- 浏览器上传后立即在来源列表看到该条目并标记「处理中」，轮询至终态。
  `CanvasResource.status` 已有 `processing`，Studio 滚轮无需新概念。

## 原因

选 A 而不是 B，是因为依赖污染是不可逆的：一旦 `unpdf` 与 `mammoth` 进入 agent-runtime，
每个引用它的包（含 gateway、node-host）都要背上这两个重依赖，之后再拆比现在建更贵。
解析是一个边界清晰的纯计算职责，值得一个自己的包。

选 A 而不是 C，是因为 C 把「解析失败」和「web 不可用」两类故障混成一类，
重试语义会变得无法推理。

不选 D，是因为 `asset_processing_jobs` 的形状已经表达了异步意图，让它继续假装是
审计表，只会让下一个读代码的人再判断一次。

## 后果

**收益**：上传响应时间与文件大小解耦；解析失败有了明确的重试位置（`attempts`）；
后续接 OCR、音视频转写不再需要第二次架构变更。

**代价**：上传语义从「返回即可用」变为「返回即受理」，前端必须处理 `processing` 态；
现存 `ready` 资产不受影响，但新旧两种写入路径要在迁移期共存到旧路径删除为止。

**风险**：worker 停机时上传会一直停在「处理中」。任务表已有 `attempts` 与
`status` 索引，恢复扫描可复用 `maintenance:delete_object_outbox` 的有界认领范式，
但本 ADR 不预先实现——先观察真实积压再决定阈值。

**后续工作**：OCR 与视频转写作为新的 job `kind` 接入，不需要再改这条流水线。

## 验证方式

- 单元测试覆盖解析器的成功与各类失败码（空文本 PDF、非 UTF-8 文本、损坏 DOCX）；
- 集成测试覆盖「上传后 asset 为 processing 且存在 queued job」与
  「worker 完成后 asset 为 ready 且 representation 已追加」；
- 手动验证：上传一个大 PDF，响应立即返回，来源列表先显示「处理中」再自动变为可用。

## 实施状态（2026-07-27）

解析器已归位到 `packages/asset-processing`，上传受理、任务入队、Worker 抽取、前端轮询
和终态提示已经接入。`render_preview` 与 `generate_thumbnail` 已补齐独立 Worker、
权威版本复核、输入上限、稳定失败码和派生对象删除链路；现有 Preview API 尚未切换为
消费派生表示。

音频转录已作为独立的初始 ingestion 状态机接入：上传只接受经容器魔术字和完整媒体
元数据验证的 MP3、WAV、Ogg、FLAC、WebM 与 M4A，最大 25 MiB、最长 60 分钟；
`assets:transcribe_audio` Worker 在调用 Provider 前重新验证当前 processing Version、
checksum、字节数、容器与时长，成功后才把 Asset/Version 推进为 `ready`。转录文本与
安全模型审计元数据属于 Version 的派生字段，原始音频仍是唯一内容事实，Provider 原文、
Prompt、对象键与堆栈不会进入浏览器投影或消息表。

恢复扫描、OCR 与视频处理仍未实现。若 Worker 长期不可用，资源仍可能停留在
`processing`，后续恢复纵切必须提供有界认领和用户可见的重试入口。
