# ADR-0012：个人 Agent 基数与模板市场边界

- 状态：`accepted`
- 日期：2026-07-27
- 负责人：项目负责人

## 背景

模板市场功能规划中出现一个产品架构问题：是否需要支持"一名用户拥有多个 Agent 实例"，还是继续"一人一个 Personal Agent，通过 Profile/Skill/模板安装组合能力"。

当前实现与文档证据：

1. **数据库约束**：`packages/db/src/schema.ts:132` 定义 `personal_agents_user_unique` 唯一索引，确保每个用户只有一个 Personal Agent
2. **ADR-0001 明确决策**："一个自然人平台用户拥有自己的个人 Agent。Agent 的私人记忆、默认 Notebook、Credential、设备配对和默认工具授权不与家庭、班级或机构成员共享。"
3. **能力组合模型**（`docs/03-ai/01-智能体编排边界.md:52-58`）：
   - Agent Profile：同一 Personal Agent 的常驻行为、目标、模型策略、预算、安全与默认工具配置，不创建新的 Agent 身份
   - Skill：按需加载的指导、模板或有限工作流
   - Tool：有双向 Schema、权限、超时和审计的动作
   - Domain Service：产生或校验可信领域事实
4. **产品定位**（ADR-0001）：EduCanvas 的第一身份是"以教育能力为核心的通用个人 Agent 平台"

## 候选方案

### 方案 A：维持一人一个 Agent，通过 Profile/Skill/模板组合能力

**用户体验**：

- 用户始终与同一个长期 Agent 交互，积累跨会话的上下文、记忆和产物
- 模板市场提供 Profile（常驻能力配置）和 Skill（按需工作流）供用户安装到自己的 Agent
- 安装模板 = 注册 Profile 或 Skill 到当前 Agent，不创建新实例
- 用户可以切换 Agent 的 Profile 来改变其行为模式（如从"通用助手"切换到"K12 教师"）

**权限模型**：

- 简单：一个用户 = 一个 Agent = 一套权限边界
- 私人 Memory、Credential、Node 配对天然隔离
- 共享 Notebook 通过显式角色授权，不传播 Agent 私人状态

**数据迁移**：

- 无需迁移：当前 schema 已满足
- 模板市场只需新增 Profile/Skill 注册表（可选）

**运行隔离**：

- 单 Agent 多 Profile 通过 Tool Policy Resolver 在同一 Runtime 内隔离
- Profile 切换是配置变更，不是进程/实例切换

**模板安装语义**：

- 安装 Profile = 注册常驻配置（模型策略、推荐工具和安全要求）
- 安装 Skill = 注册按需工作流（结构化课程、苏格拉底追问等）
- 卸载 = 从 Agent 的注册表中移除
- 版本升级 = 更新注册的 Profile/Skill 版本

### 方案 B：支持一人多 Agent 实例

**用户体验**：

- 用户可以创建多个独立 Agent（如"学习助手"、"工作助手"、"创作助手"）
- 每个 Agent 有独立的 Memory、Notebook、Conversation 历史
- 模板市场提供完整的 Agent 模板，安装 = 创建新实例
- 用户需要在多个 Agent 间切换上下文

**权限模型**：

- 复杂：需要定义 Agent 间权限边界
- 私人 Memory 需要明确归属哪个 Agent
- 共享 Notebook 需要支持多 Agent 访问同一 Notebook
- 设备配对、Credential 需要决定是 Agent 级还是用户级

**数据迁移**：

- 需要重构 `personal_agents` 表，移除 `personal_agents_user_unique` 约束
- 需要新增 Agent 选择/切换路由逻辑
- 需要处理现有用户的 Agent 迁移（默认创建一个"主 Agent"）
- Conversation、Operation、Artifact 需要重新关联到具体 Agent

**运行隔离**：

- 多 Agent 实例需要独立的 Context 装配、Tool Policy、安全策略
- 可能需要多进程或多租户隔离，增加运维复杂度
- Agent 切换需要重建上下文，可能丢失跨 Agent 的连续性

**模板安装语义**：

- 安装 Agent 模板 = 创建新 Agent 实例，复制模板的 Profile/Skill/Tool 配置
- 需要处理模板版本升级时的实例同步
- 需要处理模板删除后的实例降级

## 决定

**维持方案 A：一人一个 Personal Agent，通过 Profile/Skill/模板安装组合能力。**

## 原因

1. **产品定位一致性**：ADR-0001 明确"个人 Agent"是用户长期拥有、可持续积累上下文的主体。多 Agent 实例会稀释"个人"的含义，让用户在多个"自己"之间选择，违背产品北极星。

2. **架构简洁性**：单 Agent 模型下，权限、记忆、设备配对、Notebook 归属都有清晰的边界。多 Agent 需要重新设计整套权限模型，引入 Agent 间隔离、切换、同步的复杂度。

3. **上下文连续性**：用户与 Agent 的长期关系是产品核心价值。多 Agent 会割裂上下文，让用户在不同 Agent 间重复建立理解，降低个性化体验。

4. **教育场景适配**：K12 学生需要一个稳定的"AI 教师"形象，持续跟踪学习进度、掌握度和偏好。多 Agent 会导致学习状态分散，破坏教育可信边界。

5. **模板市场语义清晰**：Profile/Skill/模板的组合模型已经能表达"安装能力"的需求，无需引入"安装 Agent 实例"的概念。模板市场可以提供：
   - **Profile 模板**：预配置的常驻能力（如"K12 数学教师"、"编程助手"）
   - **Skill 模板**：按需工作流（如"结构化课程"、"苏格拉底追问"、"来源综述"）
   - **Tool 集合**：声明推荐工具及其能力需求；实际权限和审批仍由服务端可信策略决定

6. **数据迁移成本**：方案 B 需要大规模重构数据库 schema、路由逻辑、权限模型，且会破坏现有用户的连续性。方案 A 的迁移成本接近零。

7. **运维复杂度**：多 Agent 实例需要更复杂的资源管理、监控、备份和恢复策略。单 Agent 模型保持当前运维简单性。

## `personal_agents_user_unique` 不是缺陷

`personal_agents_user_unique` 唯一索引（`packages/db/src/schema.ts:132`）是刻意的设计约束，不是待修复的缺陷：

1. **业务语义**：一个自然人用户对应一个个人 Agent，这是 ADR-0001 的明确决策
2. **数据完整性**：防止意外创建重复 Agent，确保用户身份与 Agent 的一对一映射
3. **权限边界**：私人 Memory、Credential、Node 配对等敏感数据以 Agent 为单位隔离
4. **模板安装语义**：模板市场安装的是 Profile/Skill 能力，不是 Agent 实例，无需多实例支持

如果未来确需支持多 Agent（如企业场景下的“工作 Agent”和“个人 Agent”分离），必须
先以替代 ADR 重新定义身份、Memory、Credential、Node、Notebook 和 Operation 的归属，
再设计 Schema 与迁移。`agent_kind` 或复合唯一索引只是候选实现，不构成本 ADR 的预先决定。

但本阶段明确不做此迁移。

## 后果

- 模板市场的设计边界清晰：提供 Profile 和 Skill 模板，不提供 Agent 模板
- 用户体验保持一致：始终与同一个长期 Agent 交互，通过安装能力扩展其行为
- 架构复杂度可控：无需引入多 Agent 隔离、切换、同步机制
- 数据迁移成本为零：现有 schema 已满足需求
- 教育可信边界完整：学生与"AI 教师"的长期关系不被割裂

## 验证方式

1. 代码审计确认 `personal_agents_user_unique` 约束存在且被正确使用
2. Profile/Skill 组合模型在 Web、TUI、Gateway 已有入口保持同一 Agent 身份
3. 模板市场交付时，其设计与测试必须明确区分 Profile 模板、Skill 模板与 Agent 实例
4. 现有用户的 Agent 切换测试（如从"通用"切换到"K12"）不创建新实例
5. 共享 Notebook 场景下，成员的私人 Agent 状态保持隔离

## 与既有决策的关系

本 ADR 细化并再次确认 ADR-0001 的“一名自然人拥有一个 Personal Agent”，不替代
ADR-0001。模板市场尚未实现；这里固定的是未来产品和数据边界，不把计划中的市场能力
表述为当前已交付功能。Profile、Skill 或模板都不能绕过 ADR-0004 的权限交集。
