# ADR-0014：图像生成能力与产物信任边界

- 状态：`accepted`
- 日期：2026-07-27
- 负责人：项目负责人

## 背景

教学讲解经常需要示意图、流程图和插图。此前平台只能让模型用文字或 Markdown 描述图像，
或者要求教师自行上传素材。

图像生成同时触碰三条既有边界：它引入新的供应商能力（`packages/model-gateway`）、
产生需要长期保存的二进制内容（`artifacts` / `artifact_versions`），并让模型获得一个
有副作用、可计费的工具。若不先定清楚这三条边界的归属，最容易出现的错误实现是：把
图像塞进结构化 `StructuredModelGateway` 返回 base64、在 feature 包里另开一个模型循环、
或者让浏览器直接拿到供应商临时 URL。

## 决策

1. 图像生成使用独立的 `ImageGenerationModelGateway` Port，与 Turn、Structured、Speech、
   Transcription 并列。它不得挂到 `StructuredModelGateway` 上以 base64 字符串返回——
   二进制走结构化 JSON 入口会让预算计数、审计摘要和 Schema 校验全部失真。
2. Provider Adapter 只存在于 `packages/model-gateway`。适配器返回已通过魔术字节复核的
   字节与 `ProviderCallMetadata`；供应商原始响应体、Prompt、API Key 和堆栈止步于此。
3. 首批白名单是 PNG、JPEG、WebP 三种位图，尺寸限于 `512x512`、`1024x1024`、
   `1024x1536`、`1536x1024`，单次调用固定 1 张。SVG 等可携带脚本的矢量格式不在白名单
   内：它会把“生成一张图”变成模型可控的脚本注入通道。
4. 供应商响应中的 `url` 形态一律拒绝。内容事实必须自持在受控对象存储里，不能依赖
   供应商临时链接的有效期。
5. 生成走既有的 `artifact_generation_jobs` 耐久任务与 `artifact:generate` Graphile 任务，
   不新增内容事实表，也不在 feature 包里创建第二个 Agent Loop。浏览器只得到
   `proposed` 产物与 job 状态，永远不会在同一请求里同步拿到图像。
6. 对象写入成功后、追加版本之前保存检查点。崩溃恢复据此复用已生成的对象，不重复调用
   计费的供应商接口；检查点写入失败时先回收孤儿对象再上抛。
7. 工具 `generateCanvasImage` 在 Tool Registry 显式注册，能力名 `artifact.generate_image`，
   风险 `l1`，效果 `write`。**策略默认拒绝**：只有当模型网关已启用、Provider 为
   `openai-compatible` 且显式配置了 `MODEL_GATEWAY_IMAGE_MODEL` 时，能力才会进入
   ToolKernel 的可用集合，从而进入五维交集。未配置的部署里模型看不到这个工具，
   System Prompt 也不会提到它。
8. 生成产物固定为 `tier2`，`runtime.kind` 为 `none`，`canProduceCandidateLearningEvents`
   为 `false`。它是渲染型内容，不是判分型白名单产物，不进入任何可信学习事件路径
   （ADR-0004）。
9. CanvasResource 的 `trustTier`、`renderer`、`representation` 和 `allowedActions` 完全
   由服务端决定。生成图像只开放 `view`：`regenerate` 会重新计费且不复用基线版本，
   PATCH 修改通道也不接受这类产物，开放它会与实际后端能力不符。
10. 字节经私有读取面 `/api/v1/chat/artifacts/{id}/image` 下发，先按主体鉴权、再对完整
    对象做 SHA-256 校验。`content-type` 只取自落库 metadata 的白名单枚举，配合
    `nosniff` 与 `sandbox` CSP，保证浏览器不会把它当作页面执行。`objectKey` 与
    `checksum` 不出现在任何响应里。

## 风险等级为什么是 l1

`l1` 的判据是「写入、受控副作用，策略允许即放行」。本工具的全部副作用被当前 Notebook
包住：新增一条 `proposed` 产物和一条队列任务，用户可以归档或忽略，且不产生任何对外
分发。它与既有的 `artifact.create`（`createCanvasArtifact`）在副作用形状上完全同级。

计费风险由三处硬边界而非审批控制：单次固定 1 张、尺寸闭集、`imageMaxOutputBytes` 上限。

若将来支持把生成图像推送到 Notebook 之外——公开分享、外部投递、第三方发布——必须先
升级为 `l2` 并接上审批意图与 continuation 恢复路径，不能沿用本级别。当前 Web General
入口没有向 `resolveToolPolicy` 传入 `approvedCapabilities`，注册成 `l2` 只会让工具永远
停在 `approval_required`，那是一个不能用的能力，不是更安全的能力。

## 教育场景边界

工具只用于生成课堂讲解需要的示意图、图示与配图。它不参与出题、判分、掌握度或任何
学习证据的产生。模型在拿到 `proposed` 后必须诚实告知仍在生成，且不得描述它并没有看到
的画面细节。

## 后果

- 新增供应商能力只改配置与适配器，业务代码继续只引用 `image.generate` 任务别名；
- 未配置图像模型的部署行为与此前完全一致，不出现「答应画图然后失败」；
- 生成图像与音频概览共用同一套任务、检查点与对象存储纪律，媒体类产物不再各写一套；
- 代价是新增一条二进制读取面和一类需要长期保存的对象；对象生命周期仍遵循既有的
  object deletion outbox。

## 开放问题

- 生成配额与速率限制尚未实现。当前只有单次调用的硬边界，没有按用户或 Notebook 的
  累计预算账本；放开单次多图之前必须先补上。
- 现有 Artifact Canvas 已能通过受控媒体 URL 展示生成图像，Studio 也会列出该类产物；
  但 Web Renderer Registry 尚未迁移 `artifact.generated-image`，当前仍是详情组合层的
  兼容渲染。Registry 迁移必须作为后续独立纵切处理。
- 图像内容安全审核依赖供应商侧策略，平台没有独立的二次审核；引入面向未成年人的
  公开分享前需要重新评估。
