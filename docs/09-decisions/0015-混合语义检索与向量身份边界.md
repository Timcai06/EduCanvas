# ADR-0015：混合语义检索与向量身份边界

- 状态：`accepted`
- 日期：2026-07-27
- 负责人：项目负责人

## 背景

教材检索此前只有 PostgreSQL 全文检索（`to_tsvector('simple', …)` + GIN）。它在学生
使用教材原词提问时表现良好，但换一种说法就完全召不回：问「梯度下降怎么让损失变小」
找不到讲「反向传播更新权重」的段落，因为两者没有共同词面。

直接的做法是「装上 pgvector」。但装扩展只解决了存储，留下四个真正决定成败的问题：
向量属于谁、模型升级怎么办、两路结果如何合并、向量不可用时会发生什么。这四个问题
如果不先定清楚，最典型的失败不是报错，而是检索长期返回看似合理实则错误的结果，而
没有任何信号。

## 决策

### 向量身份

1. 向量由 `EmbeddingModelGateway` Port 产出，Provider Adapter 只存在于
   `packages/model-gateway`。它与 Turn、Structured、Speech、Transcription、Image 并列，
   不复用结构化 JSON 入口。
2. 每个向量必须随身携带完整身份：**模型、模型版本、维度、指令、切块版本**。缺任何
   一项，「这批向量能否与那批比较」就变成猜测。这五项落在
   `knowledge_chunk_embeddings` 上，其中前四项进入唯一键。
3. 模型版本由部署方显式声明（`MODEL_GATEWAY_EMBEDDING_MODEL_VERSION`）。供应商通常
   不回传版本，而同名模型换权重后旧向量必须被视为不同空间——因此配置了 embedding
   模型就必须同时声明版本，缺失即配置错误。
4. 指令区分 `query` 与 `passage` 并带版本（如 `passage:v1`）。两者产出的向量不可
   互相比较；指令升级等于一次显式重嵌入。
5. 维度是 Schema 级事实（1536），写死在 `vector(1536)` 列类型里。这是 pgvector 建
   索引的前提，也让换维度必须走新迁移 + 全量重嵌入，不能靠改环境变量悄悄切换。

### 事实边界

6. `knowledge_chunks` 仍是唯一不可变内容事实；向量只是它的派生物。整表删除向量不
   改变任何引用、判分或历史候选，只让检索退回纯 FTS。
7. `chunk_content_hash` 冗余进向量行。内容变化后的旧向量在检索时被直接排除，也自动
   重新出现在待嵌入清单里，不需要额外的失效扫描。
8. 同一 chunk 在不同模型/版本/指令下的向量可以共存。模型升级因此是「先写新向量、
   再切读、最后清旧向量」的可回滚过程，而不是一次破坏性覆盖。

### 融合与回退

9. 融合使用 Reciprocal Rank Fusion（k=60），只用名次不用原始分：`ts_rank_cd` 与余弦
   距离没有可比的量纲，任何线性加权都需要一个无法从数据推导的魔法系数。
10. 排序确定性由 `融合分 desc → chunkIndex asc → chunkId asc` 三级 tie-breaker 保证，
    同一输入永远得到同一顺序。
11. 单路召回上限为 `limit × 4`（硬上限 200）；向量子查询有 1.5 秒语句预算。超时不是
    错误而是降级信号：教学对话宁可用纯 FTS 立刻回答，也不能为等一次 ANN 扫描把整轮
    Turn 拖过用户可接受的时延。
12. **任何缺失都退回纯 FTS 并诚实标记 retriever**：未配置向量模型、查询向量生成失败、
    维度不符、向量库尚未回填、ANN 超时。绝不返回空结果冒充「没有相关内容」。
13. `retrieval_candidates.retriever` 与 `retriever_version` 必须诚实反映实际生效的
    算法。混合入口降级时使用 `postgres_fts` + `rrf-fallback-v1`，不复用纯词法入口的
    `simple-v1`：同一 (retriever, version) 只能对应一种排序语义。

### 权限

14. 权限判定先于召回。向量检索从 `turn_source_versions` 出发 join，召回范围天然被本轮
    冻结的文档限死，不存在「先全库 ANN、再按权限过滤」的窗口。

### 异步与可观测

15. 向量化是 `knowledge:embed_document` 耐久任务，由摄取任务在文档 `ready` 后入队，
    `job_key` 按文档冻结。摄取本身不因向量化失败而失败。
16. `knowledge_embedding_runs` 记录每个 (文档, 向量身份) 的状态与进度。没有它，一个
    持续失败的文档只会表现为「检索结果比预期少」，运维看不到任何信号。
17. 账本只保存状态、计数和稳定失败码，不保存教材正文、查询原文、Prompt 或供应商响应。
    检索候选同样不保存学生查询原文，只保存 `query_hash`。
18. 分批推进（单次任务最多 8 批）：一个文档可能有上万切块，一次全量嵌入会让任何中途
    失败都退回起点。进度落库后单调向前，重投继续而不是重做。

## 不做

- 不删除 `tsvector` 与 GIN 索引。纯词法入口 `retrieveFts` 保留为最小依赖的可用路径。
- 不在 Web 请求内同步嵌入全量文档。请求内只允许嵌入单条查询，且失败即降级。
- 不使用外部托管向量库。PostgreSQL 仍是业务事实源（见 CLAUDE.md 技术约定）。
- 不做无界历史回填。回填必须按文档分批入队，并可从运行账本读出进度。

## 后果

- 换一种说法提问也能召回相关教材，且召回原因可解释（名次融合而非黑箱打分）；
- 未配置向量能力的部署行为与此前完全一致；
- 代价是每个切块多一份 1536 维向量的存储与一次异步嵌入成本；
- HNSW 索引在大量增量写入下会有构建开销，教材库的写入频率远低于检索频率，这个取舍
  是划算的。

## 开放问题

- 相关性质量目前只有固定 fixture 证明的行为正确性（向量路能召回词法路召不回的内容、
  身份隔离生效），没有基于真实教材的召回率/精确率评测集。
- 重嵌入与旧向量清理尚无自动化任务：模型升级后需要人工按文档入队，旧身份的向量目前
  只能手工清理。
- 查询侧尚无向量缓存。同一 Turn 内重复检索会重复调用 embedding 接口。
- 跨用户/日的 embedding 成本预算未实现，与 Turn 模型预算是同一笔待还的债。
