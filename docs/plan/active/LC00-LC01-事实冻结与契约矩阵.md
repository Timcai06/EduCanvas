## 一、审计范围

本文档审计两条现有链路的真实实现，冻结后续开发可以依赖的事实基线，识别与 ADR-0025/0027 的差距，并建立兼容矩阵。

**审计链路：**

1. **Live 语音链路**：Agent/Turn SSE → message.delta → Turn reducer → General Workspace → VoiceComposerRuntime → 语义分段 → /api/v1/voice/live/speech → StreamingSpeechGateway → DashScope Adapter → PCM Player、字幕和取消
2. **Canvas 输出链路**：Turn outputPreference → BFF 解析 → General/Teaching profile → Canvas Artifact Tool → Graphile Worker generation job → immutable Artifact Version → CanvasResource projection → Renderer Registry 或 Tier 2 Web Runtime

## 二、LC00 事实冻结

### 2.1 Live 语音链路事实

#### 2.1.1 message.delta 流式文本增长

**文件与行号：**

- `apps/web/features/chat/turn-state.ts:431-442`

**当前事实：**

- `message.delta` 事件已直接追加到同一条 Assistant 消息
- 普通聊天具备真实流式文本事实源
- 文本通过 `message.text + event.delta` 增量增长

**Gap vs ADR-0025：** 无差距，已实现。

#### 2.1.2 Live 是否存在第二份聊天事实源

**文件与行号：**

- `apps/web/features/voice/voice-composer.tsx` (VoiceComposerRuntime)
- `apps/web/features/voice/playback/use-live-speech-playback.ts`

**当前事实：**

- Live 面板直接消费当前 Assistant 消息的投影（只读 selector）
- 语音层只保存瞬时游标、字幕和播放状态
- 退出后不产生第二份聊天记录

**Gap vs ADR-0025：** 无差距，已实现。

#### 2.1.3 TTS 消费模式：增长文本 vs 整段消费

**文件与行号：**

- `apps/web/features/voice/playback/use-live-speech-playback.ts:279-346`
- `apps/web/features/voice/playback/live-speech-segments.ts:28-70`

**当前事实：**

- TTS 会读取增长中的 `assistantText`
- 维护已消费字符 `consumedCharacters`
- 顺序入 Web Audio 队列
- 首段阈值 10–32 字，后续段 18–72 字
- 未闭合尾句等 Turn 完成才释放

**Gap vs ADR-0025：** 无差距，已实现增长文本消费。

#### 2.1.4 短语是否每段重新建立 HTTP 请求

**文件与行号：**

- `apps/web/features/voice/playback/use-live-speech-playback.ts:401-469`
- `apps/web/app/api/v1/voice/live/speech/route.ts:19-88`

**当前事实：**

- 每个短语仍单独 POST `/api/v1/voice/live/speech`
- 响应 PCM 是流式的
- 短语之间重复建连
- 缺少统一的语音提交游标

**Gap vs ADR-0025：** **存在差距**。ADR-0025 目标是连续 Speech Session，当前是逐短语 HTTP。

#### 2.1.5 显示、语音提交、播放游标

**Gap vs ADR-0025：** **存在差距**。需要引入显式的三游标状态机。

#### 2.1.6 插话与取消

## 七、后续风险

### 7.1 最高风险 Top 3

1. **Live 短语 HTTP 重连开销**：每段短语重新建立 HTTP 请求，增加延迟和连接成本。L04 需要在 `StreamingSpeechGateway` 上增加会话级提交，但当前实现是逐短语 POST。迁移需要保持字幕和播放状态机不变。

2. **outputPreference 迁移兼容性**：旧客户端只发送 `'canvas'`，新服务端需要归一化为 `'interactive_artifact'`。迁移期间需要同时支持旧值和新值，避免破坏现有功能。

3. **mind_map.v1 → v2 迁移风险**：v1 Renderer 只是递归缩进树，v2 需要边布局、视口、折叠等完整交互。历史 v1 Artifact 必须继续渲染，不能静默失效。迁移需要显式版本注册和 fixture 回放。

### 7.2 其他风险

- **dom_exploration → web_app.v1 升级**：当前 Tier 2 Runtime 基础有限，升级需要完整源码 manifest、构建诊断和发布包契约，同时保持旧 `dom_exploration` Artifact 可运行。
- **未锁依赖和超限输出**：当前只有部分检查，需要在 C06 中全面实现 fail closed。
- **性能预算未测量**：所有延迟指标都是 unmeasured，需要在 L08/C08 中通过 fake Provider 和 fixture 测量。
