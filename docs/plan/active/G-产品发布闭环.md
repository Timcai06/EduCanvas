# 核心教育产品闭环、真实试点与发布治理

- 任务分配名：`G 产品发布闭环`
- 状态：`active`
- 负责人：项目负责人
- 实现执行：项目负责人 + 协作 Agent，每次只领取一个原子任务
- 代码审核与最终验收：Codex；试点结论需人工负责人签字
- 最后验证时间：2026-08-06
- 当前领取任务：`G00`
- 前置计划：[R 运行时收敛](R-运行时事实收敛.md)、[W 工作面画布](W-工作面画布收敛.md)、
  [Q 质量观测成本](Q-质量观测成本.md)
- 关联计划：[KM 知识记忆](KM-知识记忆.md)、[UV 画布语音](UV-画布语音.md)

## 一、目标

本线处理两轮审计中最容易被继续基础设施开发掩盖的问题：

> EduCanvas 已经证明能构建可信 Agent 基础设施，但尚未用一条冻结的核心用户流程、
> 真实教育效果、生产部署演练和独立发布证据证明它是一个可持续产品。

本阶段只冻结一条主产品闭环：

```text
用户创建或进入 Notebook
→ 上传教材/课堂资料
→ 基于可追溯证据提问与讲解
→ 生成练习
→ 服务端判分
→ 给出可解释的下一步建议
→ 用户能查看来源、产物和学习记录
```

阶段结束后必须验证：

1. 所有开发优先级都能映射到上述闭环，不能再用长期平台愿景为任意基础设施扩张背书；
2. 核心流程有真实用户任务、成功指标、失败阈值和人工观察协议；
3. 产品声明与代码事实一致，不把 Canvas 协议统一、语音工程解锁或 CI 通过写成用户能力完成；
4. 至少完成一次受控试点，记录任务成功、证据质量、学习效果、延迟、成本和退出原因；
5. 正式认证、隐私权利、备份恢复、限流、观测、发布和回滚有演练证据；
6. 发布必须有独立审查，不能由同一 GitHub 身份完成实现、Codex 审核标记和最终批准；
7. 本线不新增多 Agent、渠道数量、虚拟人、长视频或其它无法直接提升主闭环的展示功能。

## 二、范围与非目标

### 本阶段范围

- 冻结核心用户、场景、任务和价值主张；
- 建立产品验收、试点和事件分析；
- 完成核心流程的端到端可靠性；
- 补正式 IdP/Session production boundary、隐私操作、备份/PITR、限流和发布演练；
- 形成可公开或内部评审的真实证据包；
- 删除或降级与主闭环无关的入口、文案和“已完成”宣称。

### 非目标

- 不同时服务所有年龄、学科、渠道和设备；
- 不完成全部 Memory、语音、Experiment Runtime 或高风险 Node；
- 不拆微服务；
- 不追求大规模 DAU；
- 不把竞赛演示视频或负责人自测当作真实试点；
- 不收集未成年人敏感数据作为默认评测材料；
- 不用模型自评代替服务端事实和人工观察。

## 三、前置门禁

- `G00-G02` 可在 R/W/Q 进行时并行，只定义产品与评测契约；
- `G03` 端到端产品收口要求 R/W 的相关 P1 问题完成；
- `G04` 试点要求 Q 的观测、成本和评测基线完成；
- `G05-G06` 发布治理要求正式部署依赖和恢复演练可执行；
- 任一前置计划处于 `BLOCK` 时，不得通过缩小证据口径把 G 线标记完成。

```text
硬边界：

- 不以新增平台能力、渠道、Agent 数量、动画或演示素材替代用户价值；

- 实际命令、退出码、截图或部署证据；
- 未通过案例、退出原因和不能推出的结论；
- 发布、回滚、隐私和安全检查；
- rtk git diff --check/name-status/status。
```

## 六、原子任务

### G00：冻结核心用户、任务与产品主张

- 依赖：无
- 文件边界：产品/路线图 canonical 文档、本计划
- 可并行：否

必须回答：

- 首个核心用户是谁；
- 他在什么真实场景使用；
- 最常完成的三个任务是什么；
- 为什么不是普通 ChatGPT、NotebookLM 或简单 RAG；
- 哪些能力是核心、辅助、实验和禁用；
- 哪些长期愿景暂不影响近期优先级。

完成标准：

- 一句话定义不再同时承担个人 Agent 平台、全渠道、全教育、代码实验等所有卖点；
- 核心流程、入口和退出条件清楚；
- 路线图中的每个 active 任务能映射到主闭环，否则暂停、降级或归档；
- 不删除长期愿景，但明确其非当前发布承诺。

### G01：任务成功指标与试点协议

- 依赖：G00
- 文件边界：产品、质量、隐私、试点文档和合成夹具
- 可并行：是

为主闭环定义：

- Task completion；
- 来源可追溯率；
- Unsupported claim rate；
- 练习与判分一致性；
- 学习前后测或纠错效果；
- 用户完成时间和放弃点；
- P50/P95 延迟；
- 单任务成本；
- 失败、降级和人工介入率；
- 用户是否理解系统限制。

试点协议必须包含：

- 招募与授权；
- 未成年人监护边界；
- 数据最小化、保留期和删除；
- 样本量和不能推出的结论；
- 任务脚本和观察表；
- 中止条件；
- 负面案例记录。

完成标准：

- 指标与 Q 线采集能力一致；
- 不使用模型自评作为唯一质量指标；
- 试点材料不含真实 Secret、未经授权教材或学生隐私。

### G02：产品状态、文案与能力门禁诚实化

- 依赖：G00
- 文件边界：产品文档、README、功能状态、必要 UI 文案和 capability health
- 可并行：是

建立统一状态：

- `available`
- `experimental`
- `disabled`
- `degraded`
- `planned`

要求：

- Canvas “统一”只描述真实统一范围；
- 语音工程任务通过不等于产品语音输入可用；
- Memory 未实现必须显式 unavailable；
- Channel 没有 live credential 不得宣称可用；
- Production 未完成 IdP/SLO/PITR 不得写 production-ready；
- 用户界面和 README 使用同一事实来源或自动生成状态摘要。

完成标准：

- 代码、UI、README、路线图和 active 计划没有互相冲突的能力状态；
- 过期 active 状态能够被检测；
- 不通过隐藏入口来伪造 capability disabled。

### G03：核心教育闭环端到端收口

- 依赖：R/W 相关任务通过，G01、G02
- 文件边界：仅主闭环需要的 Web、Teaching、Source、Artifact、判分和测试
- 可并行：否

冻结一条端到端验收：

1. 登录或受控测试身份；
2. 创建 Notebook；
3. 上传或选择授权资料；
4. 摄取并显示可用状态；
5. 基于资料回答，引用可打开；
6. 生成练习或学习 Artifact；
7. 服务端判分；
8. 写入可信学习事件；
9. 给出可解释下一步建议；
10. 刷新/重连后恢复；
11. 删除/撤权后内容不再可用。

完成标准：

- E2E 不依赖真实外部模型，使用官方格式 fixture；
- 另有受控 live smoke，失败不阻塞普通 CI；
- 无跨用户/Notebook 泄漏；
- 所有失败有诚实 UI；
- 记录端到端延迟、成本和降级；
- 非核心入口不能破坏主流程。

### G04：受控真实试点与效果报告

- 依赖：G03、Q 线完成
- 文件边界：试点数据工具、脱敏报告、产品分析文档
- 可并行：否

最低要求：

- 使用 G01 冻结任务脚本；
- 至少覆盖成功、失败、无答案、来源冲突和纠错场景；
- 记录用户行为、人工观察和系统事实；
- 报告正向与负向结果；
- 不修改评测阈值来迁就结果；
- 试点完成后按协议删除或匿名化数据。

完成标准：

- 每个指标有样本量、分母和原始证据位置；
- 结论不超过样本支持范围；
- 至少列出三个真实失败模式和对应下一步；
- 有用户价值证据，也有成本和可靠性证据；
- 负责人签字确认，不由 Agent 自行判定。

### G05：认证、隐私、备份与生产恢复演练

- 依赖：G01、Q04/Q06
- 文件边界：Auth production adapter、privacy operations、deployment/backup/runbook、测试
- 可并行：是

最低生产门：

- 正式 IdP 或明确可替换的生产身份 Adapter；
- Session 撤销、账号恢复、密钥轮换；
- 共享限流真实配置与 smoke；
- 数据导出、更正、删除；
- 对象删除闭环；
- PostgreSQL Backup/PITR；
- 对象存储恢复；
- Worker backlog 和重试；
- Telemetry Collector、SLO 和告警；
- 部署、回滚和 migration 顺序。

演练必须包含：

- 数据库误删或时间点恢复；
- Provider 不可用；
- Worker 中断；
- Telemetry 中断；
- 部署后回滚；
- Session/credential 撤销。

完成标准：

- 每个演练有时间、操作者、环境、命令、结果和恢复时间；
- 不在生产真实数据上做破坏性演练；
- 未完成项明确 blocking，不写“由云平台负责”后跳过验证。

### G06：独立审查与发布证据

- 依赖：G03、G05
- 文件边界：CODEOWNERS、branch protection 文档、release evidence workflow、发布模板
- 可并行：是

要求：

- 实现者、Codex 审核操作者和最终发布批准至少有一个独立 GitHub/组织身份；
- 关键路径 CODEOWNERS 不只指向单一仓库作者；
- PR 必须有可审计 review，而不是同一身份自我 APPROVE；
- Release evidence 包含 commit、CI、迁移、SLO、试点、隐私和回滚；
- skipped、manual、未配置项不能算通过；
- 发布后有观察窗口和回退门槛。

完成标准：

- 分支保护和 CODEOWNERS 配置有截图或 API 证据；
- 选取一个代表 PR 完成完整独立审查演练；
- release artifact 可复现；
- 不把 AI 审核工具名称当作独立性的充分证明。

### G07：阶段结论、删除决策与下一阶段冻结

- 依赖：G04、G05、G06
- 文件边界：本计划、产品/路线图/发布 canonical 文档
- 可并行：否

阶段只能得到以下三种结论之一：

- `RELEASE_CANDIDATE`
- `LIMITED_PILOT_ONLY`
- `BLOCKED`

禁止使用模糊的“基本完成”。

完成标准：

- 核心闭环、试点、治理、独立审查均有证据；
- 所有未完成能力被移出当前发布声明；
- 删除或暂停与主闭环无关的 active 任务；
- 下一阶段最多保留三个产品目标；
- 报告明确哪些问题未解决，不能用愿景段落稀释。

## 九、风险与回退

- 产品冻结可能暴露大量“已实现但非核心”的能力；默认暂停而不是强行塞入主流程；
- 试点结果不佳不等于修改指标，阶段可诚实判定 `LIMITED_PILOT_ONLY` 或 `BLOCKED`；
- 身份、隐私或恢复演练失败立即阻止发布；
- 发布演练只在隔离环境执行，保留回滚快照；
- 独立 reviewer 不可用时，保持 blocked，不使用同一身份的 AI 审核标签替代。
