## 二、核心结论（先看这个）

### 结论 1：那个第三方技能基本是坏的，但方法论有价值

- ❌ 代码全部不可运行：`setup_rag.py` 编译失败、`docker-compose.yml` YAML 解析失败、10 个关键 API 中 1 个纯虚构（`BgeRerank`）+ 7 个已弃用/路径失效
- ❌ 引用完整性 100% 断裂（SKILL.md 引用的 8 个文件 6 个缺失）；所有准确率数字（72%→97%）无出处，自认 AI 生成
- ✅ 方法论可借鉴：分块策略矩阵（按文档形态选策略）、小2大检索思想

### 结论 2：RAGFlow 能用的是一块积木——deepdoc 解析层

- **deepdoc**（PDF/扫描件/表格深度解析：OCR + 布局识别 + 表格结构识别）：Apache-2.0，可独立抽取作为 Python 解析服务
- **模型许可证已核查**：全套权重声明 Apache-2.0，无 NC 组件（双 agent 独立核查 + HF API 复核）
- ⚠️ 两个风险敞口见 §三·决策点 2
- 检索编排（两级加权魔法系数、无向量身份）**不可用**——我们的 rrf-v1 更强

### 结论 3：LlamaIndex 能用的也是两块极轻积木——Markdown 分块

- **MarkdownNodeParser**（~60 行，纯 re）：按标题层级切分，输出 `header_path`（`/h1/h2/`）——正好是我们 docs/ 语料要的章节归属
- **SentenceSplitter**（~180 行）：句子偏好合并（不切断完整句）+ 整句级 overlap
- 两者组合（标题切节 → 节内句子合并）经中文实跑对比，**胜出 naive_merge**（后者会切断完整句）

### 结论 4：检索侧不需要动，只借两个思想

- 我们的 rrf-v1 与 LlamaIndex RRF **同公式**（都源自 Cormack 论文，k=60），工程上全面更强（去重键/失败处理/可重放）
- 值得借鉴：① **多查询×多路融合**（query expansion + RRF，rrf-v2 候选）② **块补洞**（命中块 i 和 i+1 补中间块，我们连续性判断零成本）

## 三、需要你拍板的决策点

### 决策点 1：是否采纳"K 线分块器三积木拼图"

```
Markdown 文档 → MarkdownNodeParser（标题切节 + header_path）
             → SentenceSplitter（节内句子合并，注入我们 tokenizer）
PDF/扫描件   → deepdoc（OCR/布局/TSR）作为独立 Python 服务
补充能力     → naive_merge 反引号分隔符模式（按结构强制切分）
```

- **好处**：补齐 K 线最薄环节（仓库内目前**没有分块器**）；全部纯逻辑可抽取，不引入任何框架
- **代价**：需新增 Python 解析服务 + 摄取链路编排（谁触发、怎么入队、结果怎么落库，K02 工程）
- **合规**：Apache-2.0/MIT 均兼容；抽取成本 ~240 行核心逻辑 + 两个轻量依赖（tiktoken 可替换）
- 按仓库规则，落地需先走 ADR（新增 Python 服务属架构变更）

### 决策点 2：deepdoc 模型许可证的两个风险敞口是否接受

| 敞口          | 说明                                                                                                                                                 | 建议                                                                                               |
| :------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------- |
| AGPL 训练生态 | layout/TSR 权重由 YOLOv10（AGPL-3.0）/Ultralytics（AGPL-3.0）工具链产出；AGPL 对"权重=衍生作品"未表态，是法律争议，**无明确 NC/AGPL 声明落在权重上** | RAGFlow 生态及众多商用产品按 Apache-2.0 使用；如法务从严，备选 Docling（MIT）/MinerU（Apache-2.0） |
| 单方声明      | deepdoc 的 Apache-2.0 是 InfiniFlow 单方声明（HF 卡 frontmatter），仓库无独立 LICENSE 文件                                                           | HF 常见做法；正式合规决策前保留此不确定性                                                          |

**义务**：再分发保留版权声明；tsr.onnx 训练数据 PubTables-1M（CDLA-Permissive-2.0）需署名——建议在模型清单文档记录。

### 决策点 3：rrf-v2（多查询×多路融合）是否立项评估

- **收益**：扩展查询的名次多样性对 RRF 是免费收益（RRF 只吃名次）
- **冲突**：queryHash 账本语义要扩展、向量 ANN 扫描次数增加（1.5s 预算需重算）、LLM 非确定性 vs 可重放哲学
- **建议**：作为显式版本化的 `rrf-v2` 评估（扩展查询名次才允许进融合），**当前 rrf-v1 不动**

### 决策点 4：块补洞后处理是否立项

- **收益**：解决"语义检索把连续段落劈开"的常见失败模式
- **成本**：RankedChunk 自带 chunkIndex/documentId，连续性判断零成本，作为不改变检索语义的后处理
- **建议**：与 rrf-v2 一起作为 K 线检索增强的第二期
