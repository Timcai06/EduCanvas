### 升级流程

1. 用 `git ls-remote <repo> refs/tags/<tag>^{}` 解引用到新 commit；
2. 检查该 commit 的变更（release notes / diff 摘要），确认无恶意或破坏性内容；
3. 更新 `.github/workflows/*.yml` 中的 pin 与上方审计表（含日期）；
4. 更新后的 PR 必须让 dependency-review 与 secret-scan 通过。

## 二、依赖评审门禁

`ci.yml` 的 `dependency-review` job 仅在 PR 修改依赖 manifest、lockfile 或
CI workflow 时运行
`actions/dependency-review-action`（license 策略 + 已知漏洞，
`fail-on-severity: high`）。恶意或高风险依赖变更会直接阻塞合并。
`secret-scan` 不参与路径裁剪，始终运行。

## 三、容器 digest

CI 服务容器必须使用 digest，不允许浮动 tag：

- `pgvector/pgvector:pg16` → `@sha256:a36250871de0833b8757561c72f2477ef1ddd1101afa4e617fb552e0de514c6b`
  （2026-08-07 审计，用于 ci.yml integration/e2e 与 ui.yml）
- 本地 `docker-compose.yml` 是开发便利设施，不属于发布依赖，不强制 pin。

升级镜像 = 重新解析 digest（`docker pull` 后 `docker inspect --format
'{{index .RepoDigests 0}}'` 或 Docker Hub API）+ 更新本表。

## 四、模型与运行时依赖

Live Voice 只通过 `packages/model-gateway` 内的 DashScope Adapter 访问云端
ASR/TTS；仓库不下载或分发语音模型。WebSocket 客户端版本由 `pnpm-lock.yaml`
冻结，`pnpm env:check` 对北京区域端点、Workspace 和模型别名做 fail-closed
校验，且诊断不得输出 API Key。

真实供应商探针只允许从 `.github/workflows/provider-canary.yml` 手动触发。Job
绑定 `provider-canary` GitHub Environment，由 required reviewer 人工批准；API Key
与 Workspace Secret 只注入直接运行 `packages/model-gateway` canary 的 step，安装、
上传 artifact 等步骤均拿不到 Secret。输入最多 5 个冻结场景、每场景最多 2 次
Provider operation，workflow 10 分钟超时。原始 PCM 只存在内存中，artifact 仅为
SHA 绑定的脱敏聚合 summary。该 workflow 初期不加入 PR required checks；缺少
Environment/Secret 只影响人工 canary，不得降低文字、Dictation 或常规 CI 能力。

## 五、数据库迁移记录

每个 migration（`packages/db/drizzle/*.sql`）必须在
`packages/db/drizzle/MIGRATIONS.md` 有记录，字段：语义、锁表、回滚、
N-1 兼容、fresh install、预计风险。`tooling/quality/migration-records.mjs`
在 CI（quality job）校验完整性，新增 migration 无记录即失败。fresh install
由 CI integration/e2e 每次在空库跑 `db:migrate` 覆盖。

## 六、发布证据聚合

`release-evidence` job 运行 `tooling/quality/validate-evidence.mjs`，聚合测试/
retry/flaky、coverage、bundle、
migration 记录、SLO/budget、供应链评审结果，生成可追溯到 commit 与 CI
artifact 的报告。manifest（`docs/06-quality/releases/<rc>/manifest.json`）
与 schema 定义结构。

验证分为两个明确模式：

- `--mode draft`：允许 pending/running/failed，只证明结构、文件存在性、状态
  值域和数字声明内部一致；CI step 必须命名为 `Validate release evidence draft`。
- `--mode release --sha <sha>`：要求 `baseline.sha` 精确等于目标 SHA，整体状态、
  所有 gate、migration、supply-chain、eval、budget 与 signoff 全部终态通过；
  CI step 必须命名为 `Validate release readiness`。

共同聚合规则（2026-08-11 更新）：

- **failed 即失败**：任何 gate / budget / migration.fresh|upgrade /
  supply_chain 项为 `failed` → 校验失败，不允许发布；
- **skipped ≠ passed**：`skipped` 是独立状态，**绝不把 skip 写成通过**；
  每个 skipped 项必须有 `skipped_reason`/`note` 说明原因（没有理由的
  skipped → 失败）；汇总输出独立计数，不计入 passed；
- **passed 与数字一致**：带 `total`/`passed` 的 gate 写 `passed` 必须
  `passed === total` 且 `total > 0`（total=0 写 passed = 没跑却写通过）；
- **budget 一致性**：budget 项写 `passed` 必须 `actual > 0` 且
  `actual <= limit`（actual=0 或超限却写 passed → 失败）；
- **迁移可追溯**：`migration.version` 必须与磁盘迁移文件数一致
  （`packages/db/drizzle/*.sql` 计数），不一致 = manifest 陈旧；
- **终态要求**：整体 `status: passed` 时所有 gate 与 supply_chain 项
  必须已是终态（passed/failed/skipped），不允许 pending/running 冒充；
- **供应链聚合**：manifest 的 `supply_chain` 段（actions_pinned /
  dependency_review / container_digest / migration_records）汇总本章
  一~五节的评审结果，状态语义同上；
- 报告包含 baseline sha/branch/timestamp，可追溯到 commit。

最终 `checks` job 还会生成唯一的 `ci-evidence-<sha>` artifact。该 JSON 只包含
classifier 预期、lane 结果、required failures、事件和生成时间，不包含 Prompt、
Provider body、Secret、学生正文或音频。CI evidence 证明“这个 SHA 跑了什么、
结果是什么”；只有 strict release mode 才回答“是否允许发布”。

确定性 `agent-eval` 使用版本化的 `rag-v1` 与 `agent-v1` 合成数据集，不读取
Provider Secret。RAG、Tool/Artifact、Teaching Safety 的 critical 项分别过门槛，
不得用平均分抵消授权或安全失败；详细范围见 `tooling/evals/README.md`。

Live Voice 的确定性浏览器证据不调用真实 Provider：PR smoke 覆盖连续两轮与
exactly-once final，Nightly 完整故事覆盖 barge-in 的播放清空 → Turn cancel →
下一轮恢复，以及 ready Asset immutable version snapshot 和 processing Asset 排除。
真实 Provider canary、fake-provider E2E、Ego 真人麦克风验收是三类独立证据，
发布记录必须分别引用，不能以其中一类代替另外两类。

## 七、Secret scan allowlist

`.gitleaksignore` 只允许最小范围的误报条目，每条必须带解释注释
（测试夹具或公开数据，非真实密钥）。新增条目必须说明为什么安全。

## 八、责任边界

本文件与门禁只保证「可审计、可追溯、不伪装」；`skipped`/`optional` 状态的
真实含义由发布负责人在报告中显式声明，不由脚本代答。
