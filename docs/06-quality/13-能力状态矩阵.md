## 一、状态定义

| 状态 | 含义 | 判定标准 |
| --- | --- | --- |
| `available` | 可用，有回归保护 | 主路径有自动化覆盖且当前通过；失败有诚实 UI |
| `experimental` | 可见可用，但不承诺稳定 | 有实现与基本覆盖，但边界、性能或可靠性未收口；UI 必须标注 |
| `degraded` | 实现存在，但依赖缺失导致当前不可用 | 缺外部凭据/服务；UI 必须说明缺什么，而不是静默失败 |
| `disabled` | 实现存在但本阶段关闭 | 明确关闭，不是隐藏入口伪装 |
| `planned` | 未实现 | 决策可能已接受（如 ADR），但无实现；**不得出现在能力声明中** |

**关键纪律**：`planned` 与 `available` 之间没有模糊地带。ADR 接受不等于能力可用；
工程任务通过不等于产品能力可用；CI 绿不等于用户能用。

## 七、如何保持不漂移

本表的可执行约束：

1. 新增或改变能力状态的 PR 必须同时改本表；
2. 对外材料（报告、演示、README）引用本表，不各自描述；
3. 状态从 `planned` 升到任何其它档，必须给出自动化覆盖或人工证据位置。

本表不自动检测漂移——这是已知缺口。若后续要机器化，可由 `tooling/quality/`
增加一个检查把本表与 README/产品文档的能力词对齐，本阶段不做。
