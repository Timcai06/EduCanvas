## 一、需求调查

### 1.1 目标

让 EduCanvas 的**输入文档统一为带结构 Markdown**（保留标题/表格/代码块/公式层级，替代当前的"收敛为纯文本"），为后续"md 在 Canvas 中渲染（含 Mermaid 图）"打地基。

### 1.2 已对齐的需求决策（2026-08-11 与用户确认）有没有什么方式集成到我们的项目里

| 决策点                   | 结论                                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **本轮实施范围**   | 仅**Phase 1：输入统一 md**（上传文档→带结构 md 落库）；Phase 2/3 技术路线写全，供后续迭代                                |
| **转换后 md 定位** | **仅内部表示**：替换现有 `asset_versions.extracted_text`，用户看渲染结果，不可编辑 md 原文；预留后续编辑能力            |
| **Mermaid 图来源** | 文档自带`` ```mermaid `` + **模型生成 mermaid 代码块写进 md**（覆盖教学自动配图）                                         |
| **公式需求**       | **需要**：K12 数学/科学文档有公式，需渲染+保留；倾向 **MinerU**（已核实：docx 走 OMML→LaTeX，PDF 走 MFR 公式模型） |

### 1.3 现状与差距

- **现状**：上传 PDF/DOCX/Markdown/TXT + URL 导入，`extractAssetText`（`packages/asset-processing/src/text-extraction.ts`）统一收敛为**纯文本**，Markdown 结构丢失；已有 `pdf_text_unavailable` 失败码识别扫描件
- **差距**：① 无带结构 md；② 无公式保留；③ 无 Mermaid；④ 无"输入统一格式"的既有 PRD/ADR

### 1.4 需求要点细化

- **输入格式覆盖**（本轮）：PDF（文本层）、DOCX、Markdown、TXT、以及公式/扫描类复杂文档
- **转换输出**：GFM 风格带结构 Markdown，公式为 LaTeX 行内/块（`$...$` / `$$...$$`），供 react-markdown + rehype-katex 渲染
- **不在本轮**：Canvas 渲染增强、Mermaid 渲染、输出统一 md 规范、OCR、网页→md、用户编辑 md

## 二、技术路线

> 全阶段路线，Phase 1 为**本轮实施**，Phase 2/3 为后续迭代（记录备查）。

### Phase 0：现状基线（已完成）

- `text-extraction.ts` 纯文本抽取 + `extract-asset-text` worker 落库 `text/plain` + `extracted_text` 双写；Source 渲染器已能渲染 `source.markdown`

### Phase 1：输入统一 md（本轮实施）★

**1. 转换引擎选型：方案空间对比（2026-08-11 深调后更新）**

| 方案                                  | 组成                                                               | 优点                                                                                                                | 代价                                                                                                                                           |
| ------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 仅 MinerU 单引擎**（推荐） | 所有格式（docx/pptx/xlsx/pdf/txt/md）统一走`mineru-api` 独立服务 | 单一输出契约；公式全覆盖；中文/扫描 PDF 支持；docx/pptx/xlsx 秒级零模型；用户已日常使用、质量有信任背书；无边界判定 | Python 服务部署 + 模型下载 ~2GB、磁盘 20GB+、内存 16GB 起；无 GPU 时 PDF 仅`pipeline` 精度（86.47）；并发默认 3 需调优；无内置认证需自建网关 |
| B. anydoc+MinerU 双轨                 | 常规格式进程内 anydoc，复杂/公式/扫描走 MinerU                     | 轻量格式快、anydoc 免部署                                                                                           | 双引擎双契约；边界判定维护成本；anydoc 无公式无 OCR；对 K12 中文教学文档覆盖弱                                                                 |
| C. MinerU 核心+轻量兜底               | 默认 MinerU，仅纯文本小文件降级                                    | 契约以 MinerU 为主                                                                                                  | 降级路径仍要维护第二引擎，复杂度接近 A，收益小                                                                                                 |

**推荐 A（仅 MinerU 单引擎）**，理由：

- "输入统一 md"的核心是**契约统一**，单引擎最干净；MinerU 五大后端共用同一套输出契约（`.md` + `content_list_v2.json` + `middle.json` + `images/`，已核实 `docs/zh/reference/output_files.md`）
- **Office 覆盖零模型成本**：docx/pptx/xlsx 走纯解析 office 后端（秒级、读原生结构、质量最高、不受 GPU 有无影响）——这正是 K12 教师最常上传的 docx 讲义
- **公式全覆盖**：docx OMML→LaTeX（`mineru/model/docx/tools/math/omml.py`）、PDF MFR 公式模型（unimernet / 中文需 `MINERU_FORMULA_CH_SUPPORT=true`）
- 用户已日常使用 MinerU（Windows 桌面端），对转换质量有真实信任背书
- 不再引入 anydoc，减少一个原生 .node 依赖面与 ADR 项

**2.1 设置选项全景（MinerU 配置面，2026-08-11 源码核实）**

> 集成 worker 时的必查资料；下文所有参数/变量/字段均出自克隆源码，非文档转述。

**① 服务启动参数（`mineru-api`，`fast_api.py:1399-1410`）**

| 参数 | 默认 | 说明 |
|------|------|------|
| `--host` | 127.0.0.1 | 绑定地址；绑 `0.0.0.0` 即全网卡可达 |
| `--port` | 8000 | 服务端口 |
| `--enable-vlm-preload` | False | 启动即预载 VLM，首个任务快；占显存 |
| `--allow-public-http-client` | 关 | **安全闸门**：绑公网地址时默认禁止 `*-http-client` 后端 + server_url（防远程 VLM 被第三方滥用），需显式开启 |
| `--reload` | 关 | 开发热重载 |

**② 引擎后端（`backend_options.py`，每任务可选）**

| 后端 | 要求 | 精度(OmniDocBench) | 说明 |
|------|------|------|------|
| `pipeline` | 纯 CPU 可跑 | 86.47 | 稳定多语种 |
| `vlm-engine` | GPU 8GB+ | 95.30 | 高精度中英 |
| `hybrid-engine`（**默认**） | GPU 8GB+ | 95.39 | `effort` 可选 `medium`/`high`（默认 medium）|
| `vlm-http-client` / `hybrid-http-client` | 远程 OpenAI 兼容 VLM | — | 本机仅编排，不动模型 |

> 后端可随任务切换（CLI `-b` / API 请求体）：复杂 PDF 走 hybrid，docx 强制 office 秒级零模型——无需起多个服务。

**③ 每任务转换选项（`mineru` CLI / API 请求体，`client.py:1037-1185`）**

`-p` 输入文件 · `-o` 输出目录 · `-u` 远程URL · `--api-url` 连远程API · `-b` 后端 · `-e` effort · `-l` 语言 · `-m` 方法(txt/ocr/auto) · `-f` 公式开关(默认开) · `-t` 表格开关(默认开) · `-s/-e` PDF 起止页 · `--image-analysis` 图像分析 · `--client-side-output-generation`(服务端只回 middle.json、本机生成 md，省跨网流量)

**④ 关键环境变量（约 50 个，列集成相关核心项）**

| 分类 | 变量 | 用途 |
|------|------|------|
| 并发 | `MINERU_API_MAX_CONCURRENT_REQUESTS` | 默认 3；11GB 显存起步设 1 |
| 保留/清理 | `MINERU_API_TASK_RETENTION_SECONDS` | 结果 zip 保留时长，默认 86400（24h）|
| 超时 | `MINERU_TASK_RESULT_TIMEOUT_SECONDS` / `MINERU_TASK_RESULT_DOWNLOAD_TIMEOUT_SECONDS` | Node 侧超时须给足（结果等待 3600s）|

| 显存调度 | `MINERU_VIRTUAL_VRAM_SIZE`、`MINERU_DEVICE_MODE` | 多 worker 显存分配 |

**⑤ 配置文件（`~/mineru.json`，`config_version 1.3.2` 已实测）**

- `models-dir.pipeline / .vlm`：模型根目录；`model-source`：模型源（模型已本地化后可用 `local` 纯离线）
- `latex-delimiter-config`：公式定界符（display `$$..$$`、inline `$..$`）——**锁定默认**，前端 rehype-katex 直接消费

**3. 集成架构（推荐：独立服务 + REST，不做进程内 spawn）**

```
Next.js worker ──multipart POST /tasks──▶ mineru-api:8000 (Python 独立服务 / Docker)
     │                                     │
     │◀──轮询 GET /tasks/{id}──────────────┤
     │◀──GET /tasks/{id}/result (zip)──────┤
  解压 zip（Node 侧必须做 zip-slip 路径穿越校验）
  落库：content_list_v2.json 作结构化主源 + md 作展示层 + extracted_text 兼容双写
```

- **不做** `child_process.spawn('mineru', ...)`：模型加载占 20GB+ 内存、长时间阻塞事件循环、Serverless/多实例不兼容
- **认证**：mineru-api 无内置认证 → 内网/VPC 部署 + Next.js 网关 + TLS
- **文件大小上限**：服务端无显式限制，Node 侧自行控制上传上限
- **错误映射**：任务失败只有 `failed` + error 字符串，Node 侧须解析文案分类（损坏/加密/超时/模型错误）映射稳定码

**4. 集成落点（已核实现有源码）**

- `packages/asset-processing/src/text-extraction.ts`：新增 MinerU 远程调用分支输出 GFM md；原纯文本抽取保留为降级（服务不可用时），不删除
- `apps/worker/src/tasks/extract-asset-text.ts`：落库内容类型改 `text/markdown`、存储键 `derived/text/<sha>.md`；**`extracted_text` 旧字段同事务双写镜像**（兼容读，类似 D04）
- 失败码扩展：`conversion_unavailable`、`mineru_service_unavailable`、`mineru_parse_failed` 等稳定码，遵守 W03"失败不伪装成空"
- 表格输出是**原生 HTML 而非 GFM 管道表**（pipeline 侧未做样式清洗）：渲染走 rehype-raw + HTML 白名单清洗；结构化存储主源用 `content_list_v2` 的 `table_body`

**5. 服务与依赖（需过 ADR）**

- MinerU 独立 Python 服务（`mineru-api`）：模型离线预下载，`MINERU_MODEL_SOURCE=local`；**已确认 GPU（2080 Ti 11GB）→ 默认 hybrid-engine，PDF 走最高精度**
- 许可合规：Apache-2.0 + 附加条款（在线服务须署名、超规模门槛需商业授权）——ADR 记录边界
- 高吞吐扩展：`mineru-router` 挂多 worker（健康检查/自动重启/负载评分）

**6. 验收标准**

- 上传 docx/PDF（含公式样本）→ 产出带结构 md，标题/表格/代码块/公式保真
- 渲染侧零改动仍能打开（`source.markdown` 渲染器直接消费）
- `pdf_text_unavailable` 语义保留（扫描件明确走 MinerU pipeline OCR）
- 失败诚实：unsupported/malformed/encrypted/服务不可用区分，不返回空串

### Phase 2：Canvas 渲染增强（含 Mermaid）★后续

- **Mermaid 渲染**：Tier 1 **服务端预渲染 SVG + `<img>` 呈现**；自研 rehype 插件 + headless 渲染服务（`mermaid.render()` → `data:image/svg+xml`）；照抄 kroki 三道防线（request interception 网络白名单断 SSRF、secure 数组锁死防 `%%{init}%%` 降级、maxTextSize/超时/并发上限）——**安全机制已源码核实**
- **模型生成图**：让模型产出 `` ```mermaid `` 代码块写进 md（而非直接调图服务），保留可编辑+可导出
- **md 文档查看器增强**：现有 `source-resource-renderer.tsx` / `note-renderer.tsx` 补 Mermaid 插件；如需可加目录/长文档性能
- 依赖：playwright/chromium 或外部渲染服务（需 ADR）

### Phase 3：输出统一 md + 文档 artifact 判断 ★后续

### 后续扩展（记录备查）

## 三、风险与约束

| 风险/约束            | 说明                                                                              | 缓解                                                               |
| -------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| MinerU 服务资源      | Python 服务 + 模型下载 ~2GB、磁盘 20GB+、内存 16GB 起                             | 纯 CPU 可跑 pipeline + office；模型离线预下载；批量走异步队列      |

| MinerU 并发/失败粒度 | 默认并发 3；任务失败仅`failed`+error 字符串                                     | mineru-router 多 worker；Node 侧解析 error 文案分类映射稳定码      |

| 信任模型             | 不执行模型生成 HTML/JS                                                            | md 渲染走预注册 Renderer；Mermaid 服务端预渲染（Phase 2）          |
