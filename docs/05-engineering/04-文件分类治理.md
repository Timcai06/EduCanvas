# 仓库文件分类治理

- 状态：`accepted`
- 生效日期：2026-08-08
- 执行入口：`pnpm file:check`

本规范覆盖 Git 跟踪的全部文件。治理的目标是让文件位置和责任可判断、可审计，
不是把现有 `apps/` 与 `packages/` 架构整体重排。

## 一、四维分类

`tooling/quality/file-governance.mjs` 对每个 tracked file 给出四个维度：

| 维度      | 回答的问题                                   | 示例                                                  |
| --------- | -------------------------------------------- | ----------------------------------------------------- |
| location  | 文件属于仓库根、应用、包、测试、工具还是文档 | `apps`、`packages`、`tooling`                         |
| domain    | 谁拥有业务语义                               | `web`、`db`、`agent-runtime`、`cross-system`          |
| role      | 文件承担什么技术职责                         | source、test、configuration、migration、documentation |
| lifecycle | 文件当前如何维护                             | maintained、verification、generated-record、archived  |

所有文件必须完成分类；实际处置只有五种：保持、移动、拆分、退役，或冻结增长并
推迟到一个明确的任务线。分类完成不等于每个文件都必须移动。

## 二、位置和命名规则

- 仓库根目录只放全仓入口、工作区配置和跨平台启动文件；新增根文件必须显式加入治理白名单。
- 产品运行代码进入 `apps/<surface>` 或 `packages/<capability>`；单一 Agent loop 仍只属于 `packages/agent-runtime`。
- 跨仓库开发工具按职责进入 `tooling/local/`、`quality/`、`e2e/`、`architecture/` 或 `testing/`；`tooling/` 根层不直接堆放脚本。跨系统黑盒测试进入 `tests/`。
- 迁移 SQL 与 Drizzle meta 是生成记录，不手工移动或改写。
- 禁止跟踪 `.next`、`dist`、`build`、`coverage`、`.turbo`、`output`、`node_modules` 等产物目录。
- 禁止 `.md.md`、`.json.json` 等重复扩展名。
- `docs/` 根层只保留文档入口；历史审计、旧实施计划和只读基线统一进入 `docs/archive/`。
- `pnpm file:check` 同时验证仓库内 Markdown 相对链接，移动文件必须同步修复有效链接。

## 三、编辑器配置

`.vscode` 不应整体忽略。仓库只跟踪下面两份无密钥、跨成员共享的配置：

- `.vscode/settings.json`：格式化、仓库 TypeScript SDK 与 ESLint 工作目录；
- `.vscode/extensions.json`：ESLint、Prettier 与 Tailwind CSS 推荐扩展。

其余 `.vscode/*` 保持 gitignore；治理门禁也会拒绝误跟踪的 `launch.json`、个人任务、
断点或机器路径。因此共享体验可复现，同时个人编辑器状态不会进入版本库。

## 四、文件体积债务

生产型源码在 400 行进入复核区，通常应在 600 行前按职责拆分。现有达到 400 行的
文件记录在 `tooling/quality/file-size-baseline.json`：允许缩小，不允许静默增长，
新增达到阈值的源码必须先拆分或经过显式治理决策。

当前超过 600 行的既有债务按以下边界处理：

| 债务范围                                   | 处理边界                                              |
| ------------------------------------------ | ----------------------------------------------------- |
| `packages/db/src/schema.ts`                | D05 专属；本轮不提前修改 schema 或 migration          |
| DB repository 大文件                       | 在 D02-D08 对应数据任务触达时拆分；治理门禁先冻结增长 |
| `packages/agent-runtime/src/agent-loop.ts` | 后续 Runtime 专项拆分，禁止建立第二个 Agent loop      |
| Voice transport 大文件                     | 由 UV 语音线拥有，跨线治理不得抢改                    |
| Teaching projection 大文件                 | 后续 teaching-core 专项拆分，保持领域事实权威         |

基线是债务上限，不是“超大文件合理”的永久豁免。

## 五、CI 影响分流

CI workflow 始终启动一个轻量 `changes` job，并由
`tooling/quality/ci-impact.mjs` 根据 base/head 文件差异选择后续 lane：

| 变更类型                                                     | checks                | integration | windows | runtime-pressure | e2e    | dependency-review |
| ------------------------------------------------------------ | --------------------- | ----------- | ------- | ---------------- | ------ | ----------------- |
| `docs/` Markdown、根/模块 README、CODEOWNERS、共享 `.vscode` | 跳过                  | 跳过        | 跳过    | 跳过             | 跳过   | 跳过              |
| 普通源码/工具                                                | 运行                  | 按路径      | 按路径  | 按路径           | 按路径 | 跳过              |
| 依赖锁、workspace manifest、CI workflow                      | 运行                  | 运行        | 运行    | 运行             | 运行   | 运行（仅 PR）     |
| 手动 workflow dispatch 或无法可靠求 diff                     | 全量运行（fail-open） | 全量        | 全量    | 全量             | 全量   | 全量（PR 时）     |

`secret-scan` 不参与裁剪，所有事件始终执行。路由只减少无关成本，不降低受影响域的
断言、覆盖率或 E2E 强度。CI 不使用 workflow 级 `paths` 跳过整个 required workflow；
选择发生在 job 级，避免 required check 因 workflow 未创建而长期 pending。branch
protection 继续只依赖稳定的 `checks` 汇总 job；它会验证密钥扫描和所有本次应运行的
lane 均成功，因此被裁剪的 job 不会造成假失败，真实失败也不能被 skipped 掩盖。

## 六、变更要求

1. 新增顶层目录、根文件、共享编辑器文件或生成记录位置时，必须同时更新治理规则和测试；
2. 新模块优先保持单一命名责任，不以新的聚合大文件偿还旧债；
3. 修改 CI 路由时必须添加路径分类测试，未知路径或无法比较 SHA 一律全量运行；
4. 文件治理与 D05 schema 模块化分开验收，治理 PR 不得产生 schema/migration diff。
